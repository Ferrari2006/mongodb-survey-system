# MongoDB 问卷系统课程项目

目标是完成符合题目的系统，并让学生能解释设计、验证实现、真实记录 AI 协作。执行范围由本次请求决定：需求分析不自动升级为整套开发，准备交付不自动授权公开发布仓库。

## 需求与证据

- 开始相关工作前读取 [课程基线](references/course-baseline.md)。基线是已核对的摘要；用户提供新文档或课堂补充时重新核对，并注明来源和变化。
- 区分文档明确要求、用户转述的课堂要求、待确认解释和建议。新信息发生冲突时指出冲突，不静默覆盖。
- 维护需求到设计、实现、测试、交付证据的对应关系。标明未实现、未运行或尚未确认，不能用计划代替完成结果。
- 技术方案先作为候选方案讨论，记录学生实际选择及理由；不可把三个集合、特定框架或目录名称写成教师指定要求。
- 第二阶段必须在第一阶段基础上演进，保留基线代码、旧数据和回归用例。具体变更以届时的新需求为准。

## 输出对象

每次撰写讲解、报告或演示前读取 [表达与记录规范](references/audiences-and-evidence.md)。

- 对学生：说明概念、取舍、操作、失败原因和待决定事项，联系 Lab2 CRUD 与 Lab3 聚合、索引；帮助学生作出并理解选择。
- 对教师：依据真实证据组织需求、设计理由、关键机制、实现、测试和 AI 使用说明；少写操作教程和逐行代码解释。
- 两种表达共享同一事实底稿。不能将 AI 建议改写成学生独立想到的内容，不能虚构修改、测试或对话。必要逻辑和 AI 披露不得因压缩表达而消失。
- 用户未指定时，解释性问题默认面向学生；提交报告、答辩材料、README 默认面向其实际读者。学习笔记与提交材料分开存放。

## 实施工作流

1. 根据现有成果选择切入点，不重复已完成工作。先列当前需求、验收条件及影响实现的歧义。
2. 围绕访问方式讨论集合划分、嵌入与引用、字段类型、稳定 ID、约束、索引、答卷增长、发布后的结构修改和匿名语义。解释为什么适合 MongoDB，不声称关系数据库不能实现问卷系统。
3. 定义 API 的输入、输出、认证、所有权、状态及错误行为，再按可验证功能逐步实现。前端朴素但操作完整。业务数据存 MongoDB。
4. 跳转和校验由数据配置驱动；后端验证答案和实际有效路径。明确多规则冲突、默认路径、无效目标、循环、分支切换、被跳过必答题的处理。未获确认的限制标为暂定设计。
5. 尽可能用真实 MongoDB 操作支持需求：CRUD、嵌套字段和数组查询、聚合统计及有依据的索引。不能为展示操作而添加无用功能。
6. 测试至少覆盖课程六类要求，并按风险增加权限、截止状态、匿名、重复填写和并发检查。逻辑测试用 assert 检查预期；API 测试验证状态码、响应和数据库效果；页面流程另行验证。业务输入校验不用 assert 替代显式错误处理。
7. 使用独立测试数据库和明确测试数据。实际运行后记录步骤、输入、预期、实际及结果；失败也如实保留。测试通过仅覆盖已运行范围。
8. 持续记录本次真实 AI 提示词、建议或代码、学生反馈、接受或修改理由、验证结果及代码定位。示例提示词不可当成已发生对话。
9. 交付前核对需求覆盖、可运行说明、Schema、API、关键逻辑、测试和报告的一致性。报告说明为什么设计、证据是什么、限制是什么。第二阶段再检查数据兼容和旧功能回归。

## 完成判定

根据用户当前任务报告实际产物与未完成事项。完成需求分析不意味着系统完成；静态检查不意味着 API 已运行；生成报告不意味着仓库已提交。不要承诺“完全符合”而缺少逐项证据。
