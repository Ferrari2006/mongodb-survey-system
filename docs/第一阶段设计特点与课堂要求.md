## 2. 自身特点及它们解决的问题

1. **已确认进度独立保存。** fill_progress可反复更新，responses只收正式提交；刷新恢复与统计口径互不干扰。当前未确认输入不自动保存，边界明确。
2. **进度和答卷都受有效路径约束。** 返回修改清理后缀，后端重算路径，避免跳过的必答题阻挡和旧分支数据污染。
3. **统计值可核对。** 多选按本题有效份数作分母；0不当成空值；facet让同次字段使用同批输入。已有真实图和精确聚合断言。
4. **区分不同种类的版本与标识。** schema_version处理结构，revision处理编辑／进度冲突，request_id处理同次重试，submission_key处理重复策略，各自有用途。
5. **异常有实际复现。** 覆盖未来版本竞争、长文本、重复点击、响应乱序、加载失败及并发防重。测试案例是独立数据库中的真实执行，不只看页面成功提示。

这些是本项目已有的设计组合与工程改进，不能宣称其他项目没有、也不能宣称为新的通用算法。38项记录来自2026-10-22实际执行；当前只改报告，没有删除、重写或另增业务功能。

## 3. 保留的实现与后续范围

账号、本人问卷、所有题型、可配置跳转、发布／截止／关闭、分享填写、匿名和重复控制、进度恢复、分支清理、聚合与分页答卷及本轮边界修正全部保留。

发布冻结、向后跳转、登录后匿名、统计按答卷份数是当前明确的实现约定，并非教师逐项指定。后续变更依第二阶段原文处理，保留旧代码、数据与回归用例。当前不将完整题目版本、共享题库、跨问卷统计写成已经实现。

## 4. 个人理解的检查点

学生可亲自解释：为什么需要fill_progress与responses两个集合；q1改答后哪些内容保留／清理；被跳过必答为何不阻挡；多选两份各选两项为何可显示两个100%；request_id与revision为何不能混用。个人实际操作、判断和发现的新问题可据实补入日志，不预先编造成验收经历。
